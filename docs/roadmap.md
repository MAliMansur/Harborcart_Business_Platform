# Twelve progressive engineering phases
This delivery expands the application used throughout the project. It does not skip the learner's gates. Only the local implementation checks listed in evidence/VERIFICATION.md have been executed.

Every phase requires a scenario, prerequisites, exact implementation commands for the chosen environment, reviewable configuration, expected outcomes, observed evidence, one incident exercise, a rollback/recovery check and an interview. Future phase implementation packets are produced after the preceding gate and its decisions are reviewed; they are not represented as completed infrastructure in this repository.

| Phase | Business scenario and prerequisites | Work and completion gate | Incident and interview |
|---|---|---|---|
| 1. Requirements and architecture | Equipment procurement must cross buyer, manager, warehouse and finance boundaries. No cloud prerequisites. | Review business.md, architecture.md, decisions.md and cost plan. Pass preflight; record scope and risks. | Missing tool/runtime mismatch. Explain supported branch versus patched release; choose reservation policy. |
| 2. Linux, Git and business runtime | Team needs reproducible local transactions. Phase 1 decisions recorded. | README setup, first-gate.md, automated tests, real HTTP exercise, reconciliation and recovery. Create a branch and reviewed commit. | HC-01/02/04; investigate stuck invoices and duplicate submissions. Explain process health versus business health. |
| 3. Containers and PostgreSQL | Several processes must share durable inventory safely. Gate B1 passed. | Dockerfile/Compose, migration/runtime roles, B2 commands, all PostgreSQL races executed, persistence and resource limits verified. | Last-unit race, DB connection and permission failures. Explain transaction isolation and privilege boundaries. |
| 4. CI and supply chain | Every business-rule change needs evidence before release. Phase 3 passed. | Run supplied GitHub CI, hash locks, source/dependency/image scans, SBOM, branch rules and required reviewers. Verify a deliberately failed PR is blocked. | Failed CI/dependency incompatibility or secret exposure guard. Explain what repository settings YAML cannot enforce. |
| 5. Local Kubernetes and Helm | Rolling deployments must preserve service. Container behavior proven. | Build local-cluster chart with separate web/worker deployments, migration job, probes, requests/limits, service, ingress, PDB and policy. Verify rollout and rollback before cloud. | CrashLoopBackOff, missing env/secret, bad image, failed rollout. Diagnose events, previous logs and rollout history. |
| 6. Observability and SLOs | Accepted orders must be invoiced on time. Runtime behavior and owners understood. | Execute local Prometheus/Grafana profile; validate alerts; add request counters/latency histograms, independent alert delivery and burn-rate rules for approved SLOs. | Monitoring failure, missing series and silent backlog. Explain why dashboards do not establish an SLO. |
| 7. Terraform and AWS guardrails | A controlled cloud lab is requested. Explicit region, budget and spending approval required. | Design least-privilege access, backend/state locking, VPC, cost tags and expiry. Review plan and estimated costs before any apply. | State conflict, IAM denial, drift. Explain safe lock ownership investigation; never force-unlock blindly. |
| 8. EKS and managed data | The team needs a cloud operating environment. Approved plan and local Helm gate. | Implement EKS, private RDS, ECR, ingress/TLS, workload identity, secrets and network controls. Apply only within explicit approved scope; prove connectivity and restore. | DNS, routing, security group/CNI and database failures. Trace request and credential paths. |
| 9. GitOps with Argo CD | Production changes require traceable promotion. Cloud runtime validated. | Separate reviewed environment config, immutable image digests, sync controls, RBAC and protected promotion; validate drift and rollback. | Failed sync, bad manifest and accidental configuration drift. Explain source of truth and emergency-change reconciliation. |
| 10. Capacity and reliability | Procurement demand spikes at quarter end. Valid observability and workload model. | Run controlled load/soak tests, measure p95 and throughput, database locks/connections, HPA behavior, queue age and cost. Set budgets from evidence. | Resource exhaustion, slow DB, worker backlog. Explain the bottleneck before scaling. |
| 11. Disaster recovery and incidents | Orders and financial records must survive failures. Verified backups and isolated restore target. | PostgreSQL/RDS restore, PITR, RPO/RTO measurement, cutover/rollback, incident communication and postmortem. | Data failure, unavailable dependency and failed recovery. Prove data correctness and customer recovery, not just process restart. |
| 12. Readiness and portfolio | A release candidate is proposed. All earlier evidence reviewed. | Readiness review, risk acceptance, approvals, cost/teardown review and honest portfolio. Publish only verified claims. | Timed mixed incident and technical interview; defend decisions, limits and improvements. |

## Evidence required at every phase
Use evidence/templates/phase-gate.md. Attach actual commands and exit statuses, relevant configuration/commit IDs, incident report, corrective change, rollback/recovery results, cost record where relevant and interview answers. Mark each item proposed, executed, passed, failed or untested.

A phase passes when you can explain the system and diagnose its failure with evidence. Completion of a personal lab is valuable portfolio evidence; it is not employment history or an automatic substitute for years on call.
