# Gate B1: operate the business workflow locally

Business scenario: a branch needs network equipment. Purchasing, warehouse and finance must complete their own part without sharing authority.

Prerequisites: new repository extracted separately; Python 3.12–3.14, Git and Make. Your previous Python 3.12.15 is sufficient for this local gate. A missing unzip binary is irrelevant after extraction. Use the currently selected Python interpreter to create the new .venv; do not replace the OS Python.

## Setup and expected output
Run the README startup commands. Expected:
- preflight: python_supported_for_project true and required tools true; exit 0;
- migrations: applied successfully;
- seed: two fictional workspaces, seven accounts, 17 products and ten purchases;
- check: no Django system-check issues, no pending model changes;
- test: all applicable tests pass; three PostgreSQL tests explicitly skipped on SQLite;
- login page at localhost:8080 and a second terminal running the worker.

If an existing seed is detected, setup says it preserved the data. Counts can differ after your own purchases. Do not reset data just to make it match the starting example.

## Exercise
1. Sign in as buyer. Open the catalog. Add four Managed network switches; select EAST; enter a fictional delivery address. Submit.
2. Save the order number and displayed state. Explain why available stock and available credit changed before dispatch.
3. Sign out, sign in as manager. Open Purchasing approvals and review the buyer, amount, warehouse and destination. Approve.
4. The worker should move the purchase from queued to confirmed and create one invoice. Refresh the order. Record the invoice number.
5. As warehouse, pack, dispatch and record delivery. Check inventory after dispatch.
6. As finance, record the complete payment using a unique reference such as LAB-B1-PAY-001. Check the company's available credit.
7. As buyer, request a full return with a reason.
8. As warehouse, confirm goods received. As finance, record refund reference LAB-B1-REFUND-001.
9. As operator, inspect the order, audit trail and operations center. Run:
```bash
make reconcile
make recovery
python scripts/smoke_http.py
```
10. Sign in as rival and try the Atlas order URL you saved. It must return 404. Try /operations/ as buyer; it must return 403.

For accounts to have separate browser sessions, use separate browser profiles or sign out between roles. The password is local-only and generated by bootstrap.

## Validation and evidence
Record actual output in evidence/my-gate-b1.md using the evidence template. Include order/invoice identifiers, timestamps, expected versus observed stock/credit, reconciliation output, a restore evidence filename and any failures. Redact passwords, tokens, personal addresses and cookies.

The refund is a ledger record. It must not be described as an actual payment-provider refund. Recovery here verifies a local SQLite copy, not RDS point-in-time recovery.

## Investigation exercise — do this before reading solutions
Scenario: the buyer can sign in and place a purchase, but a newly approved order remains queued. The web health endpoint returns 200.

Write three hypotheses, decide which evidence distinguishes them, and explain why restarting the whole application might be an inappropriate first response. Use docs/drills.md for the controlled local exercise. Root causes and corrective actions are in a separate solutions file.

## Completion criteria
- Complete the purchase-to-refund journey using the appropriate role at each handoff.
- Explain credit commitment, reservation release and the difference between a live web process and a healthy business workflow.
- Show one recorded invoice and one recorded settlement per reference.
- Demonstrate tenant and role boundaries with observed HTTP results.
- Pass reconciliation, automated tests and the isolated HTTP exercise.
- Save restore evidence and a short incident report.
- Propose and justify one policy change without implementing it yet.

## Technical interview
1. A browser times out after checkout. What evidence determines whether retrying is safe?
2. Why must stock availability be checked inside the checkout transaction?
3. What can a successful /healthz response fail to tell you?
4. A worker dies after claiming a job. What permits another worker to recover it, and what prevents the old worker from committing later?
5. Which claims are still unproven while the tests use SQLite?
6. Would a 30-minute reservation fit a business where approvals take two days? Explain the costs of your alternative.

Assessment: 0 = guesses without evidence; 1 = identifies a component; 2 = tests competing hypotheses and validates recovery; 3 = also explains customer impact, data invariants, prevention and the limits of the evidence. Aim for 2 or better on every question before the container gate.
